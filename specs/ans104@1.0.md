# `ans104@1.0` — ANS-104 DataItem codec & commitment device

- **Device name:** `ans104@1.0`
- **Depends-on:** `structured@1.0` (TABM ⇄ rich codec), `message@1.0` (the
  commitment/ID surface this device plugs into). Compare with `httpsig@1.0`
  (the default commitment device, whose role this device plays for the ANS-104
  format). All three specs are provided to reimplementers.
- **Status:** Draft

## 1. Overview

`ans104@1.0` is **both a codec and a commitment device** for the external
**ANS-104** "bundled data item" standard. As a codec it maps a TABM
(Type-Annotated Binary Message, see `structured@1.0`) to and from an ANS-104
**DataItem** — the binary record (signature, owner, target, anchor, tags, data)
that Arweave gateways and the wider `arbundles` ecosystem understand. As a
commitment device it can `commit` (sign) a message as a DataItem and `verify`
that DataItem's signature, exposing the result to `message@1.0` as an ordinary
commitment.

The point of the device is **interoperability**: a message committed through
`ans104@1.0` produces bytes that are bit-for-bit a valid ANS-104 DataItem, and
any valid ANS-104 DataItem (e.g. one produced by `arbundles.js`) decodes into a
HyperBEAM message whose commitment verifies. Because the DataItem byte layout is
**content-addressed** — the message's ID is derived from those exact bytes — this
spec pins the wire format precisely. A single wrong byte yields a different ID
and a broken signature.

A DataItem may also carry **nested DataItems** (a *bundle*); the codec can fold a
message's sub-messages into a bundle and unfold them back, gated by a `bundle`
flag.

## 2. Concepts & terminology

- **ANS-104 DataItem (or "item"):** the external standard's signed record. It has
  these logical fields: a **signature type**, a **signature**, an **owner**
  (public key), an optional **target** (32 bytes), an optional **anchor**
  (32 bytes), an ordered list of **tags** (each a `name`/`value` pair of arbitrary
  binaries), and a **data** payload (a binary, or — when bundled — a nested set of
  items). This spec treats the standard's byte format as normative (§5).
- **Tag:** a `{name, value}` pair where both are arbitrary binaries. Tags are
  **ordered** and tag names are **case-preserving** and **may repeat**. This is
  unlike message keys, which are lowercase, hyphenated, and unique.
- **Field (base field):** the DataItem's `target` and `anchor`. They live in
  dedicated positions in the byte layout (not in the tag list), each 32 bytes when
  present.
- **TABM:** the flat, all-binary message form this codec converts to/from. The
  codec is named for the format it produces *from* TABM; conversion between
  ANS-104 and HyperBEAM's rich representation always routes through TABM via
  `structured@1.0`.
- **Commitment:** an entry in a message's `commitments` map (see `message@1.0`)
  attesting to a DataItem signature (or, for an unsigned item, to its content ID).
  Its `commitment-device` is `ans104@1.0`.
- **Bundle:** a DataItem whose `data` is itself a sequence of nested DataItems,
  indexed either positionally (a *list bundle*) or by name through a manifest (a
  *map bundle*). Marked by the reserved tags `bundle-format` / `bundle-version`
  (and, for map bundles, `bundle-map`).
- **base64url:** the only on-the-wire encoding for binary IDs, owners,
  signatures, targets, and anchors carried in message/commitment keys. 32-byte
  values encode to 43 characters. **Hex MUST NOT be used.**

## 3. Device interface

- **Dispatch shape:** this device exposes a fixed set of named keys: the codec
  keys `from` and `to`, the commitment keys `commit` and `verify`, the
  serialization keys `serialize` and `deserialize`, and `content-type`. It does
  **not** install a default handler and does **not** answer arbitrary data keys;
  message inspection/mutation (`keys`, `set`, …) and the `id` / `committers` /
  `committed` surface are inherited from `message@1.0` operating over the message
  this codec produces.
- **Inputs to `from` / `to`:** the value to convert as the base, plus a request
  that MAY carry a `bundle` boolean (§6). `to` accepts a TABM map, a DataItem, or
  a bare binary; `from` accepts a DataItem or a bare binary.
- **`content-type`** returns the fixed string `application/ans104`.

## 4. Resolved keys (normative)

### `to` — message (TABM) → ANS-104 DataItem
- **Reads:** the value to convert (`Base`); `bundle` from `Req`, else from the
  matching `ans104@1.0` commitment's `bundle` key, else from node options
  (default `false`); the message's `ans104@1.0` commitment if present (for
  signature material and original tags); node options (for loading nested
  links when bundling).
- **Behaviour:** Produce the DataItem whose byte layout (§5) round-trips to the
  message. Specifically:
  1. **Bare binary input** MUST produce a DataItem with a single tag
     `{ao-type, binary}` and the binary as `data`, no other fields. (This lets a
     naked binary be addressed/serialized; `from` recognises the marker and
     unwraps it.)
  2. **An existing DataItem input** is returned unchanged.
  3. **A TABM map input:**
     a. Locate the message's commitment whose `commitment-device` is
        `ans104@1.0` (if any). If more than one matches, error
        `multiple-ans104-commitments-unsupported`.
     b. If `bundle` is true, fully load any linked sub-messages and re-encode
        with sub-messages kept inline so they become nested items; the original
        message's commitments are preserved over the loaded copy. If `bundle` is
        false, sub-messages are not offloaded into the bundle.
     c. **Signature material:** if a matching commitment exists, reconstruct the
        DataItem's `signature`, `owner`, `signature_type`, `target`, `anchor`,
        and original tag list from that commitment (§5.5). Otherwise start from an
        unsigned item (zero signature, zero owner) and take `target`/`anchor` from
        the message's `target`/`anchor` keys when they decode to valid 32-byte IDs.
     d. **Data:** compute the `data` payload (§4.`data-mapping`).
     e. **Tags:** compute the tag list (§4.`tag-mapping`).
     f. **Normalise:** recompute `data_size` and both IDs (§5.3) from the
        assembled fields.
  4. Any other input MUST error `invalid-tx`.
- **Returns:** `{ok, DataItem}`.
- **Side effects:** when `bundle` is true, MAY read linked sub-messages from the
  store to materialise them inline. No writes.

### `from` — ANS-104 DataItem → message (TABM)
- **Reads:** the DataItem (`Base`); `bundle`-irrelevant here (always unfolds a
  present bundle); node options.
- **Behaviour:** Produce the TABM that round-trips back to this DataItem.
  1. **Bare binary input** returns itself unchanged.
  2. A DataItem **tagged `{ao-type, binary}`** returns its `data` binary
     directly (inverse of `to` rule 1).
  3. Otherwise, fully deserialize the item (unfolding any nested bundle), then:
     a. **Fields → keys:** a present `target` / `anchor` becomes a message key
        `target` / `anchor` whose value is the base64url of the 32 bytes.
     b. **Tags → keys:** decode the tag list to keys (§4.`tag-mapping` inverse):
        normalise each tag name (lowercase), aggregate duplicate names into a
        single Structured-Fields list value, lower-case the keys named inside any
        `ao-types` tag, and drop the metadata tags (`bundle-format`,
        `bundle-version`, `bundle-map`, `ao-data-key`, and a bare `data` tag) from
        the top-level keys (they are preserved inside the commitment, §5.5).
     c. **Data → keys:** if `data` is a nested bundle (map/list), recurse `from`
        over each child and merge them in under their bundle keys; if `data` is a
        plain binary, place it under the key named by an `ao-data-key` tag if
        present, else under `data`; an empty `data` contributes nothing.
     d. **Committed key set:** compute the ordered list of keys the item commits
        to (§5.4).
     e. **Base message:** assemble exactly the committed keys, sourcing each from
        data, then fields, then tags (in that precedence). A committed key that
        cannot be found MUST error `missing-key`.
     f. **Commitment:** attach a `commitments` entry keyed by the item's ID
        (§5.5): a **signed** commitment if the item carries a signature, an
        **unsigned** commitment if the item is unsigned but its tags are not all
        already normalised (so the original tag order/case must be recorded), and
        **no commitment at all** if the item is unsigned and every tag is already
        a normal lowercase key (the message is simply its own content).
- **Returns:** `{ok, TABM}` (or `{ok, Binary}` for the binary cases).
- **Side effects:** none.

### `tag-mapping` (used by `to`/`from`) — which keys become tags
- **Message-key → tag direction (`to`):** every committed, non-reserved key whose
  value is a binary short enough to be a tag (§5.6 limits) is emitted as a tag
  `{key, value}`, in the committed order. Keys placed in `data` (the data key and
  any nested-bundle keys) are NOT also emitted as tags. If the data key is not
  the literal `data`, an `{ao-data-key, <key>}` tag is prepended. Bundle metadata
  keys (`bundle-format`, `bundle-version`, `bundle-map`), when present in the
  matching commitment, are emitted as the **leading** tags. A signed item whose
  commitment recorded an `original-tags` list MUST reproduce that exact tag list
  (names, values, order, case) instead of the normalised derivation.
- **Tag → message-key direction (`from`):** see `from` step (b). Tag names are
  matched case-insensitively and normalised to lowercase keys.

### `data-mapping` (used by `to`/`from`) — what fills the `data` payload
- **`to`:** Choose the **data key**: an explicit `ao-data-key` value if the
  message carries one; else `body` if the message has a non-link `body` key and no
  `data` key; else `data`. Collect sub-messages: every non-reserved key whose
  value is a nested message, or whose key/value exceeds the tag-size limits
  (§5.6), becomes a nested item. If there are nested items, the result is a
  **bundle** (map of those items, plus the data-key's own value as an item if it
  is set); otherwise the result is the plain binary at the data key (or empty).
  The reserved keys `commitments`, `data`, and `target` are never treated as
  bundle members during this collection.
- **`from`:** inverse, per `from` step (c).

### `commit` — sign (or content-stamp) a message as a DataItem
- **Reads:** the target message (`Base`); `type` from `Req`; the node's
  `priv-wallet` for signed types.
- **Behaviour:** Normalise `type` then act:
  - `signed` is an alias for `rsa-pss-sha256`; `unsigned` is an alias for
    `unsigned-sha256`.
  - For a **signed type** (`rsa-pss-sha256`, `ed25519-sha512`, or `ethereum`):
    convert the message (with private keys reset) to a DataItem, sign it with the
    configured wallet, and convert the signed DataItem back to a message — yielding
    a message with an `ans104@1.0` **signed commitment** added. The wallet's key
    type MUST match the requested signature type, else error
    `wrong-wallet-to-sign`.
  - For **`unsigned-sha256`:** remove any existing `commitments`, round-trip the
    message through ANS-104 and back (forcing tag normalisation and recomputation
    of the content/unsigned ID), and return it.
- **Returns:** `{ok, CommittedMessage}`.
- **Side effects:** none beyond reading the wallet from options.

### `verify` — check an ANS-104 commitment
- **Reads:** the message (`Base`) and the selecting `Req` (which commitment(s) to
  check, per `message@1.0` selection).
- **Behaviour:** Reduce the message to only the selected commitment(s), reset
  private keys, convert to a DataItem, and verify that DataItem (§5.7): its ID
  MUST equal SHA-256 of its signature, its signature MUST verify against its owner
  and signature type over the signature preimage (§5.2), and its tags MUST be
  within the count/size limits. Return the boolean result.
- **Returns:** `{ok, Boolean}`.
- **Side effects:** none.

### `serialize` — message/DataItem → bytes
- **Behaviour:** If given a message, first `to` it into a DataItem, then emit the
  ANS-104 byte layout (§5.1). If given a DataItem, emit its bytes directly.
- **Returns:** `{ok, Binary}`.

### `deserialize` — bytes → message (TABM)
- **Behaviour:** Accept a binary (or a request carrying the bytes under `body`),
  parse it as a single ANS-104 DataItem (§5.1), then `from` it into a TABM.
- **Returns:** `{ok, TABM}`.

### `content-type`
- **Returns:** `{ok, <<"application/ans104">>}`.

## 5. Data formats & encodings (normative — byte-exact)

All multi-byte integer fields below are **little-endian** unless stated.

### 5.1 DataItem byte layout
A serialized DataItem is the concatenation, in order:

1. **Signature type** — 2 bytes: the type code then `0x00`. Codes:
   `1` = RSA-PSS (RSA 4096, exponent 65537), `2` = ed25519, `3` = ethereum
   (secp256k1/eth), `4` = solana. (So RSA is `01 00`, ed25519 `02 00`, etc.)
2. **Signature** — fixed length by type: RSA 512 bytes; ed25519 64; ethereum 65;
   solana 64. An unsigned item carries the all-zero signature of the RSA length
   (512 zero bytes) by default.
3. **Owner** (public key) — fixed length by type: RSA 512 bytes; ed25519 32;
   ethereum 65; solana 32. An unsigned item carries the all-zero owner of the RSA
   length.
4. **Target** — a presence byte: `0x00` for absent, or `0x01` followed by exactly
   32 bytes.
5. **Anchor** — same presence-byte encoding as target, 32 bytes when present.
6. **Tag count** — 8 bytes, the number of tags.
7. **Tag bytes length** — 8 bytes, the byte length of the encoded tag blob that
   follows.
8. **Tags** — the Avro-encoded tag blob (§5.6). When there are zero tags, fields
   6 and 7 are both 8 zero bytes and the blob is empty.
9. **Data** — the remaining bytes (the payload, or the serialized bundle).

### 5.2 Signature preimage (what gets signed / hashed)
The signature is computed over a **deep-hash** of this ordered list of binaries
(the same construction the ANS-104 standard specifies):

```
[ "dataitem", "1", <sig-type-string>,
  <owner>, <target>, <anchor>, <encoded-tags>, <data> ]
```

- `"dataitem"` and `"1"` are the literal UTF-8 ASCII strings.
- `<sig-type-string>` is the UTF-8 ASCII decimal of the type code: `"1"` RSA,
  `"2"` ed25519, `"3"` ethereum, `"4"` solana.
- `<owner>`, `<target>`, `<anchor>`, `<data>` are the raw field bytes (empty
  binary when the field is absent).
- `<encoded-tags>` is the Avro tag blob of §5.6 (empty binary when no tags).

The **deep-hash** is the Arweave deep-hash: for a binary `B`,
`H( H("blob" ++ dec(len B)) ++ H(B) )`; for a list `L`, fold
`Acc := H(Acc ++ deephash(elem))` starting from `Acc := H("list" ++ dec(len L))`.
`H` is **SHA-384**; `dec(n)` is the ASCII decimal of `n`; `++` is byte
concatenation. (This SHA-384 deep-hash is internal to the preimage only.)

### 5.3 ID derivation (base64url, never hex)
- **Unsigned ID (content ID):** SHA-256 of the §5.2 preimage **computed with the
  owner field replaced by the all-zero RSA-length owner**. This is the ID a
  content/unsigned commitment is keyed by, and equals `message@1.0`'s content ID
  for the message.
- **Signed ID:** SHA-256 of the **signature** bytes. This is the ID a signed
  commitment is keyed by.
- Both IDs are 32 raw bytes; they are carried in messages/commitments as their
  **43-character base64url** form. An ID MUST NOT be emitted as hex.

### 5.4 Committed key set (deterministic)
The keys a DataItem commits to are the **deduplicated union**, in this order:
1. the **data keys** — the keys contributed by the `data` payload, in ascending
   sorted order;
2. the **tag keys** — each tag's normalised (lowercased) name, in tag order,
   **excluding** the metadata tags `bundle-format`, `bundle-version`,
   `bundle-map`, `ao-data-key`, and a bare `data` tag;
3. the **present base fields** — `target` and/or `anchor`, but only those that
   also appear among the base-fields / tags / data already gathered.

Any `+link` suffix is stripped from each committed key. This ordered list is what
the commitment records under `committed`, and it determines the tag/field
ordering on re-encode.

### 5.5 Commitment message shape
A DataItem's commitment is one entry in the message's `commitments` map. **Key:**
the item's ID base64url (signed ID for a signed item; unsigned ID for an unsigned
one). **Value (a message):**

Common to both:
- `commitment-device` = `ans104@1.0`.
- `committed` = the ordered committed-key list (§5.4), TABM-encoded as a list.
- `bundle` = `true`/`false` (string) — whether the item carried `bundle-format`,
  i.e. is a bundle.
- `original-tags` = present **only** when the item's tags are not already all
  normalised lowercase keys; a numbered message (keys `1`,`2`,… in tag order)
  whose members are `{ name => <raw tag name>, value => <raw tag value> }`. This
  captures exact casing/order/duplication so the bytes can be reproduced. When the
  tags are already normal, this key is **absent**.
- For a **bundle**, the metadata tags themselves (`bundle-format`,
  `bundle-version`, `bundle-map`) are copied into the commitment as keys.

Signed commitments additionally carry:
- `committer` = the signer **address** base64url. The address is
  SHA-256(owner-public-key) for RSA/ed25519/solana; for ethereum it is the
  20-byte keccak Ethereum address rendered `0x…` (42 chars).
- `signature` = base64url of the raw signature bytes.
- `keyid` = the literal string `publickey:` followed by base64url of the **owner
  public key**. (On decode, the scheme prefix up to and including the first `:` is
  stripped to recover the owner bytes.)
- `type` = the signature-type string: `rsa-pss-sha256`, `ed25519-sha512`, or
  `ethereum` (see §5.8). (Also `ecdsa-secp256k1-sha256`, `solana`,
  `typed_ethereum` for the corresponding types.)

Unsigned commitments instead carry:
- `type` = `unsigned-sha256` (and no `committer`, `signature`, or `keyid`).

Any field whose value would be the "unset" sentinel (e.g. an absent
`original-tags`) MUST be omitted from the commitment, not emitted as a literal.

### 5.6 Tag encoding (Apache Avro)
Tags are encoded exactly as the ANS-104 standard's Avro array of `{name, value}`
records:
- Each integer (counts, lengths) is **ZigZag**-then-**variable-length** (VInt)
  encoded: ZigZag maps `n≥0 → 2n` and `n<0 → -2n-1`; VInt emits 7 bits per byte,
  little-endian, with the high bit set on every byte except the last.
- The blob is: ZigZag(tag-count), then for each tag `ZigZag(len name) ++ name ++
  ZigZag(len value) ++ value`, then a terminating `0x00` (the zero-count block
  marker). A zero-length name or value is encoded as a single `0x00`.
- An empty tag list encodes to the **empty binary** (and the surrounding count
  and length fields, §5.1 fields 6–7, are zero).
- Names and values are arbitrary bytes (UTF-8 text in practice). **Limits:** a tag
  name MUST be ≤ 1024 bytes, a tag value ≤ 3072 bytes, and a DataItem MUST have
  ≤ 128 tags. A message key or value exceeding the name/value limit is instead
  routed into the `data` bundle rather than a tag; a message with more than 128
  tag-bound keys MUST error `too-many-keys`.

### 5.7 Bundle (nested items) layout
When a DataItem's `data` is a bundle, the `data` payload is:
1. **Item count** — 32 bytes.
2. **Index** — `count` entries, each 64 bytes: a 32-byte item byte-length
   followed by the 32-byte item ID.
3. **Items** — the concatenated serialized items, in index order.

A **list bundle** carries tags `{bundle-format, binary}` and
`{bundle-version, 2.0.0}` and positionally indexes its items (decoded to message
keys `1`,`2`,…). A **map bundle** additionally carries `{bundle-map, <ID>}` where
`<ID>` is the unsigned ID (base64url) of a **manifest** item; the manifest is a
DataItem tagged `{data-protocol, bundle-map}` `{variant, 0.0.1}` whose `data` is a
JSON object mapping member name → member ID (base64url). Decoding resolves each
named member by ID from the bundle index. Reserved bundle-marker tag values
(`binary`, `2.0.0`) are matched case-insensitively on decode.

### 5.8 Signature-type string table
| code | preimage string | commitment `type` | signature len | owner len |
|------|-----------------|-------------------|---------------|-----------|
| 1 | `1` | `rsa-pss-sha256` | 512 | 512 |
| 2 | `2` | `ed25519-sha512` | 64 | 32 |
| 3 | `3` | `ethereum` | 65 | 65 |
| 4 | `4` | `solana` | 64 | 32 |

`unsigned-sha256` is the commitment `type` for an unsigned item; it maps back to
the RSA layout (zero owner/signature) on decode.

## 6. Ordering, freshness & caching

- **Determinism:** given a fixed message and `bundle` flag, `to` MUST be a pure
  deterministic function — committed-key order (§5.4), tag order, field placement,
  and the Avro/bundle byte layouts are all fully determined. This is what makes
  the resulting ID stable and content-addressable.
- **Tag ordering & casing:** a signed item's tags are **immutable** — their exact
  order and casing are captured in `original-tags` at decode and reproduced
  verbatim on re-encode, so a decode→encode round-trip reproduces the original
  bytes and the signature still verifies. An unsigned message with only normal
  lowercase keys derives its tag order from the committed-key order.
- **`bundle` flag:** controls whether sub-messages are folded into a nested bundle
  (`true`) or left out of the DataItem's `data` (`false`, default). It is read
  from the request, falling back to the matching commitment's `bundle`, then node
  options. The flag affects representation only, not which keys are committed.
- The device performs no result caching of its own.

## 7. Security & authority

- **Failure-closed verification.** `verify` returns `true` only if the DataItem's
  ID matches SHA-256(signature), the signature verifies against the owner over the
  exact §5.2 preimage, and the tag limits hold. Any mismatch yields `false`.
- **Signature covers exactly the committed content.** Because the signed bytes are
  derived from the fields/tags/data assembled from the committed keys, a verified
  commitment attests to precisely those keys. Per `message@1.0`, changing a
  committed key's value drops the commitment.
- **Wallet/type binding.** `commit` MUST refuse to sign when the configured
  wallet's key type does not match the requested signature type
  (`wrong-wallet-to-sign`); it MUST NOT silently downgrade or substitute a key.
- **Single ANS-104 commitment per message** for codec purposes: encountering more
  than one `ans104@1.0` commitment when one is required is an error
  (`multiple-ans104-commitments-unsupported`), never a silent pick.
- **Private keys** are reset out of the message before it is converted to a
  DataItem (so they are never hashed, signed over, or serialized).

## 8. Errors

All error atoms are hyphenated.

- `invalid-tx` — `to` was given a value that is not a binary, DataItem, or map.
- `multiple-ans104-commitments-unsupported` — a message carries more than one
  `ans104@1.0` commitment where exactly one is required (encode / signature-info).
- `missing-key` — `from` determined a key to be committed but could not find it in
  the item's data, fields, or tags.
- `missing-committed-key` — `to` was told (by the commitment's `committed` list) to
  emit a key as a tag that is absent from the message.
- `wrong-wallet-to-sign` — `commit` requested a signed type the configured
  wallet's key type cannot produce.
- `too-many-keys` — a message would require more than 128 tags.
- `invalid-signature-type` — an unrecognised signature-type string/code was
  encountered while (de)serializing the type.
- ANS-104 byte-parse failures (truncated header, bad tag section, tag-count
  mismatch, missing Avro terminator, residue, unsupported signature format) — the
  byte parser MUST reject malformed input rather than accept it. Exact atom
  spellings are an implementation detail, but malformed DataItems MUST NOT parse
  as valid.

## 9. Composition

- **As a commitment device:** `ans104@1.0` plays the same role for ANS-104 that
  `httpsig@1.0` plays by default. `message@1.0`'s `id`, `commit`, `committers`,
  `committed`, and `verify` all delegate to this device when a commitment names
  `commitment-device = ans104@1.0`. A user obtains an ANS-104 signature by calling
  `commit` with `commitment-device = ans104@1.0` (and a wallet in options).
- **As a codec:** conversions between ANS-104 and any other format
  (`structured@1.0`, `httpsig@1.0`, …) route through TABM. A message can therefore
  be signed as a DataItem, re-encoded to an HTTP-signature message, and back, with
  each format's commitment preserved.
- **Bundling** lets a structured message with nested sub-messages be serialized as
  a single ANS-104 bundle for upload to Arweave, and reconstructed on read.

## 10. Conformance (normative checklist)

An implementation MUST exhibit all of the following, each checkable via
`commit` / `verify` / codec conversion / `serialize` / `deserialize`:

1. **Codec round-trip.** A message of plain lowercase key→binary pairs converts to
   a DataItem and back to an equal message (modulo added commitments).
2. **External interop — read.** A valid ANS-104 DataItem produced by an
   independent implementation (e.g. `arbundles.js`) decodes to a message whose
   `ans104@1.0` commitment verifies, with `target`/`anchor`/tags/data recovered
   exactly.
3. **External interop — write.** A message committed via `ans104@1.0`, serialized,
   then parsed by an independent ANS-104 reader, is a valid DataItem with a
   verifying signature and the same tags/fields/data.
4. **Byte-exact layout.** A serialized DataItem matches §5.1 exactly: 2-byte
   little-endian signature type, then signature, owner, presence-prefixed
   32-byte target and anchor, two 8-byte little-endian tag count/length fields,
   the Avro tag blob, then data.
5. **ID derivation.** The unsigned/content ID is SHA-256 of the §5.2 preimage with
   a zeroed owner; the signed ID is SHA-256 of the signature; both are reported as
   43-char base64url (never hex). The content ID equals `message@1.0`'s content ID
   for the same message.
6. **Signature preimage.** Signing/verifying uses the deep-hash of
   `["dataitem","1",<type-str>,owner,target,anchor,encoded-tags,data]` with the
   SHA-384 deep-hash of §5.2; tampering with any committed field makes `verify`
   `false`.
7. **Tag encoding.** Tags encode as the §5.6 Avro array (ZigZag/VInt, terminating
   zero block); an empty tag list is the empty blob with zeroed count/length;
   duplicate tag names on decode aggregate into a single Structured-Fields list
   value; tag names are case-preserved on the wire but become lowercase keys.
8. **Field vs tag placement.** `target`/`anchor` that decode to valid 32-byte IDs
   occupy the DataItem field slots and become base64url `target`/`anchor` message
   keys; values that are not valid 32-byte IDs are carried as ordinary tags
   instead.
9. **Data key selection.** With no `data` key and a non-link `body` key, `body` is
   the data payload and an `{ao-data-key, body}` tag is added; otherwise `data` is
   the payload and no `ao-data-key` tag is added; the inverse holds on decode.
10. **Signed-tag immutability.** Decoding a signed DataItem whose tags are
    mixed-case / out of normalised order records them in `original-tags`, and
    re-encoding reproduces the byte-identical DataItem that still verifies.
11. **Commitment shape.** A signed commitment carries `commitment-device`,
    `committer` (base64url address), `committed` (ordered key list), `signature`
    (base64url), `keyid` = `publickey:<base64url owner>`, `type` (the §5.8 string),
    and `bundle`; an unsigned commitment carries `commitment-device`,
    `committed`, `type` = `unsigned-sha256`, and `bundle`, with no `committer`.
12. **`commit` type handling.** `signed` ⇒ `rsa-pss-sha256`; `unsigned` ⇒
    `unsigned-sha256`; signing with a wallet whose type ≠ the requested signed
    type errors `wrong-wallet-to-sign`.
13. **Bundling.** With `bundle = true`, a message with nested sub-messages
    serializes to one ANS-104 bundle (§5.7) carrying `bundle-format`/
    `bundle-version`, and decodes back to the nested structure; with
    `bundle = false`, sub-messages are not folded in and the commitment's `bundle`
    is `false`.
14. **Binary passthrough.** A bare binary encodes to a DataItem tagged
    `{ao-type, binary}` with the binary as data, and decodes straight back to the
    binary.
15. **`content-type`** returns `application/ans104`.

## 11. Out of scope

- The internal in-memory representation of messages, DataItems, tags, and links.
- The full ANS-104 standard text and the complete RFC-9651 Structured-Fields
  grammar (assume conforming parsers are available; this spec pins only the bytes
  the device produces/consumes).
- The cryptographic internals of RSA-PSS / ed25519 / secp256k1 signing and of the
  Arweave wallet/address derivation beyond the address rules stated in §5.5.
- v1/v2 Arweave layer-1 transaction formats (this device handles ANS-104
  DataItems only).
- Performance, storage layout, and the on-chain upload path.

## Open questions

- **Solana / typed-ethereum coverage.** The signature-type table (§5.8) lists
  solana (code 4) and the byte parser also recognises a `typed_ethereum`
  (code 7, 42-byte owner) form, but `commit` only accepts RSA, ed25519, and
  ethereum. A reimplementer should confirm which signed types `commit` must
  *produce* versus which it must only *verify/decode*.
- **Float / rich values in committed keys.** This codec carries binaries; rich
  typing is handled upstream by `structured@1.0`, which flags float encoding as
  unstable. Committed messages SHOULD avoid float-typed values until that is
  pinned, since a differing TABM byte changes the ANS-104 content ID.
- **Anchor/target acceptance asymmetry.** On decode, a tag named `target`/`anchor`
  whose value is a valid 32-byte ID is treated as the field; whether an
  application can intentionally keep a 32-byte-looking value as a *tag* (not a
  field) across a round-trip should be confirmed during validation.
