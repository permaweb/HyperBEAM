# `p4@1.0` — pay-for-process payment hook framework

- **Device name:** `p4@1.0`
- **Depends-on:** `message@1.0` (commitment / signer surface), `router@1.0`
  (non-chargable route matching, `match` key). References — but does not require
  the spec of — a **pricing device** and a **ledger device** that the operator
  configures (e.g. `simple-pay@1.0`, `faff@1.0`, `metering@1.0`); the contract
  those devices MUST satisfy is pinned in §4.4–§4.5 below.
- **Status:** Draft

## 1. Overview

`p4@1.0` ("pay-for-process") is the **payment gate** of a node: a pair of
request/response hook handlers that decide whether the node will service a
request and charge the caller for it. It implements no pricing or accounting
logic itself. Instead it delegates to two pluggable sub-devices named in its
own handler configuration:

- a **pricing device**, which estimates and finalises the *cost* of a request;
  and
- a **ledger device**, which holds per-account **balances** and applies
  **charges**.

p4 sits as a node's `on/request` and `on/response` hooks. **Before** a request
is evaluated it asks the pricing device for an estimate and (if the estimate is
positive) checks the caller's balance with the ledger device, denying the
request with HTTP `402` if funds are insufficient. **After** the request has
been evaluated it asks the pricing device for the final price and instructs the
ledger device to charge the caller's account, crediting a configured recipient.
It also exposes a `balance` key so a caller can query its own balance through
the configured ledger.

A single device, `simple-pay@1.0`, can act as *both* the pricing and ledger
device; `faff@1.0` is a degenerate allow-list policy that prices admissible
callers at `0` and everyone else at `infinity`. p4 is agnostic to which
policies are plugged in — it only speaks the contract in §4.

## 2. Concepts & terminology

- **Hook handler:** a message, bound to this device, installed under a node's
  `on` configuration for a named lifecycle event. The node resolves the handler
  with the event's request message; the handler returns `{ok, NewReq}` to let
  the pipeline continue or a non-`ok` result to halt it. p4 is installed as the
  handler for the `request` and `response` events (and typically the same
  message for both — see §9).
- **Pre-request hook (`request`):** runs *before* the node evaluates the
  request. Its job is to *gate*: estimate cost, check balance, allow or deny.
- **Post-response hook (`response`):** runs *after* the node has produced a
  result. Its job is to *settle*: determine the final cost and charge it.
- **Handler configuration (`Base` / "State"):** the message bound to this
  device under `on`. It carries the two configuration keys `pricing-device` and
  `ledger-device` (§3), plus any other keys the policy devices read (e.g.
  `ledger-path`, `module`). When p4 invokes a sub-device it does so by taking
  this configuration message and overriding its `device` key with the
  sub-device's name, so the sub-device sees the *whole* handler configuration as
  its base.
- **Pricing device:** a device implementing the keys `estimate` and `price`
  (§4.4). Estimates/prices are non-negative integers, the integer `0`, or the
  binary `infinity`.
- **Ledger device:** a device implementing the keys `balance` and `charge`
  (§4.5). It holds an opaque per-**account** balance.
- **Account / caller:** the **signer** (committer) of the request being
  serviced. p4 resolves this from the request's commitments (§7). A request with
  exactly one signer is charged to that signer; the multi-signer and unsigned
  cases are handled per §4.
- **Price / cost:** the numeric quantity returned by the pricing device.
  `infinity` means "never serve, at any price". `0` means "free — proceed
  without touching the ledger". A positive integer is a chargeable amount passed
  to the ledger.
- **Chargable request:** a request whose path does **not** match the node's
  configured non-chargable route set (§4.3). Non-chargable requests bypass
  pricing and charging entirely.
- **Request singleton:** the raw, unparsed request message the node received
  over HTTP, supplied to hook handlers under the `request` key of the hook's
  request message. p4 reads its signers and its `path` from this.
- **Body:** the parsed sequence of messages the node will evaluate
  (pre-request) or the result of evaluation (post-response), supplied under the
  `body` key. p4 passes `body` through unchanged on every allow path.

This device defines no AO-Core IDs, commitments, or content-addressed artefacts
of its own. The one commitment it produces is a signature over the `charge`
request it sends to the ledger (§4.2, §5).

## 3. Device interface

- **Dispatch shape:** **explicit keys.** The device answers exactly three keys —
  `request`, `response`, `balance` — and nothing else. It is **not** a
  default/resolver device and has no catch-all handler; resolving any other key
  against a message bound to this device falls through to the base
  `message@1.0` device. `request` and `response` are intended to be invoked only
  as hook handlers; `balance` is intended to be invoked as a normal resolved key
  (typically via the path `~p4@1.0/balance`).

- **Handler configuration keys** (read from `Base`, the handler message, by
  ordinary key lookup; binary, lowercase, hyphenated on the wire):

  | Key | Meaning | Default |
  |---|---|---|
  | `pricing-device` | Device name of the pricing sub-device (e.g. `simple-pay@1.0`, `faff@1.0`, `metering@1.0`). | absent → treated as the sentinel "unset" |
  | `ledger-device` | Device name of the ledger sub-device (e.g. `simple-pay@1.0`). | absent → treated as the sentinel "unset" |

  When **either** `pricing-device` or `ledger-device` is unset, p4's gating is a
  **no-op that allows** (§4.1): the request proceeds and nothing is charged. An
  operator MUST set both to actually gate or charge. The handler message MAY
  carry any additional keys the chosen policy devices need; p4 passes the whole
  configuration message to them as their base and does not interpret those extra
  keys.

- **Node-options inputs** (read from node options, not from the handler message).
  Read each via its **atom** key (e.g. `p4_non_chargable_routes`, `p4_recipient`,
  `operator`): the node-option lookup canonicalizes an atom key to its
  lower-hyphenated binary form, so a single atom-key read matches the operator's
  value whether they declared it under the snake or the hyphen spelling shown
  below. (Reading a raw binary key does **not** fold spellings — use the atom.)

  | Option | Meaning | Default |
  |---|---|---|
  | `p4_non_chargable_routes` / `p4-non-chargable-routes` | A route-match list (the `router@1.0` route syntax) whose matching paths are **not** charged. | the default set in §4.3 |
  | `p4_recipient` / `p4-recipient` | Address credited by the post-response charge. | unset → fall back to `operator` |
  | `operator` | The node operator's address; the charge recipient when `p4_recipient` is unset. | unset → the literal `unknown` |

  A node also conventionally configures `http-extra-opts` so hook resolution is
  not served from the result cache, but that is a platform concern and out of
  scope here.

- **Hook request message** (the message p4's `request`/`response` keys are
  resolved against): MUST carry
  - `request` — the raw request singleton (used for signer extraction and path);
  - `body` — the sequence of messages to evaluate (`request` hook) or the
    evaluation result (`response` hook). Passed through opaquely.

## 4. Resolved keys (normative)

### 4.1 `request` — pre-request gate

- **Signature:** `request(Base, Req) -> {ok, #{ body }} | {error, ErrMsg}`.
- **Reads:**
  - From `Base` (handler config): `pricing-device`, `ledger-device`, and (passed
    onward) every other key of the config.
  - From `Req`: `body` (the message sequence) and `request` (the raw singleton).
    `body` MUST be read with hashpath updates suppressed so reading it does not
    perturb the request's hashpath.
  - From node options: the non-chargable route set (§4.3).
- **Behaviour:**
  1. Determine whether the request is **chargable** by matching its `path`
     against the non-chargable route set (§4.3).
  2. **If not chargable:** return `{ok, #{ <<"body">> => Body }}` immediately —
     no pricing, no ledger, no charge.
  3. **If chargable but `pricing-device` or `ledger-device` is unset:** return
     `{ok, #{ <<"body">> => Body }}` — gating is disabled, the request proceeds
     free. (This is the fail-**open** default that makes an unconfigured node
     usable; §7.)
  4. **If chargable and both devices are set:** build the pricing base by taking
     `Base` and overriding `device => pricing-device`. Resolve its `estimate`
     key (§4.4) with a request of:
     ```
     { path: "estimate", request: <raw singleton>, body: <message sequence> }
     ```
     Then:
     - **`{ok, infinity}`** → **deny**: return
       `{error, <<"Node will not service this request under any circumstances.">>}`.
     - **`{ok, 0}`** → **allow**: return `{ok, #{ <<"body">> => Body }}` (free;
       no balance check).
     - **`{ok, Price}`** (any other `ok`-tagged value — normally a positive
       integer) → proceed to the balance check (step 5) with that value as
       `Price`. (The match for a usable price is "the result is `{ok, _}` and is
       neither `infinity` nor `0`"; p4 does not itself re-validate that `Price`
       is numeric — a non-numeric `{ok, _}` flows into the balance comparison,
       where the ledger reply governs the outcome.)
     - **any non-`ok`-tagged result** (e.g. `{error, _}`, or any other tag) →
       **deny** with an error message
       `{ type: <result-tag>, body: "Could not estimate price of request." }`.
       The `type` field reflects the tag of the unexpected result (e.g.
       `error`).
  5. **Balance check.** Build the ledger base (`Base` with
     `device => ledger-device`) and resolve its `balance` key with:
     ```
     { path: "balance", target: <account>, request: <raw singleton> }
     ```
     where `<account>` is the request's sole signer; if the request has **no**
     signer it is the binary `unknown`; if it has **multiple** signers the value
     is the list of signers (§7). Interpret the ledger's reply:
     - **`{ok, true}`** or **`{ok, infinity}`** → **allow** (the ledger
       guarantees sufficiency without revealing a number).
     - **`{ok, Balance}`** with `Balance >= Price` → **allow**.
     - **`{ok, Balance}`** with `Balance < Price` → **deny** with HTTP `402`
       (§4.6, insufficient funds), echoing `price` and `balance`.
     - **`{error, _}`** → **deny** with HTTP `500` (the ledger could not be
       consulted; §4.6).
  6. On every **allow**, the result is exactly `{ok, #{ <<"body">> => Body }}` —
     the message sequence is passed through and nothing else is added.
- **Returns:** `{ok, #{ body }}` on allow; `{error, ...}` on deny (see §4.6 for
  every shape).
- **Side effects:** none of its own. The balance check is a **read** — p4 MUST
  NOT charge during the pre-request hook. (Whether the *ledger* mutates state
  during a `balance` call is the ledger's concern; p4's request to it is a
  query.) No commitments, no message-cache writes by p4.

### 4.2 `response` — post-response charge

- **Signature:** `response(Base, Req) -> {ok, #{ body }} | {error, ErrMsg}`.
- **Reads:**
  - From `Base`: `pricing-device`, `ledger-device`, plus config passed onward.
  - From `Req`: `body` (the evaluation result; read with hashpath suppressed)
    and `request` (the raw singleton).
  - From node options: the non-chargable route set (§4.3), `p4_recipient`,
    `operator`.
- **Behaviour:**
  1. If **either** device is unset **or** the request is **not chargable** (§4.3),
     return `{ok, #{ <<"body">> => Response }}` — pass the result through with no
     charge.
  2. Otherwise determine the **final price**. Build the pricing base
     (`device => pricing-device`) and resolve its `price` key with:
     ```
     { path: "price", request: <raw singleton>, body: <evaluation result> }
     ```
     - If `price` returns **`{error, _}`**, p4 MUST **fall back** to resolving
       `estimate` on the same base with the same request (path swapped to
       `estimate`) and use that result instead. (This lets a pricing device
       implement only `estimate`; §4.4.)
     - If `price` returns `{ok, P}`, use `P`.
  3. Interpret the resulting price:
     - **`{ok, 0}`** → no charge: return `{ok, #{ <<"body">> => Response }}`.
     - **`{ok, Price}`** (positive) → **charge** (step 4).
     - **`{ok, infinity}`** → **no charge** (return `{ok, #{ <<"body">> =>
       Response }}`). By §4.4, `infinity` MUST NOT be handed to the ledger as a
       `quantity`. In practice this does **not** arise — the pre-request gate
       already denied an `infinity` *estimate*, so a request reaching the charge
       step was admitted under a finite estimate — so the reference does not
       separately re-guard it here; but a request settled with an `infinity`
       `price` MUST NOT be charged.
     - **`{error, E}`** (after the estimate fallback also failed) → return
       `{error, E}` — the price could not be determined, so the response is
       turned into an error.
  4. **Charge.** Construct a charge request and **sign it with the node's key**
     (p4 commits the request because it is the *node*, not the user, performing
     the charge; §5, §7). The charge request is:
     ```
     { path: "charge",
       quantity: <Price>,
       account: <account>,
       recipient: <recipient>,
       request: <raw singleton> }
     ```
     where:
     - `<account>` is the request's sole signer; if the request has **multiple**
       signers it is the list of signers (§7). (Unlike the pre-request balance
       check, the post charge does **not** substitute `unknown` for the
       no-signer case — see Open questions.)
     - `<recipient>` is, in order of precedence: the human-readable form of
       `p4_recipient` if it is a valid address; else the human-readable form of
       `operator` if set; else the binary `unknown`. A **valid address** here is a
       configured (non-`undefined`) value accepted by the substrate's native-ID
       validity check — i.e. a 32-byte native address **or** its 43-character
       base64url encoding — which is then rendered to that canonical base64url
       (human-readable) form. An unset or non-address `p4_recipient` falls through
       to `operator`.
     Resolve the ledger base (`device => ledger-device`) with this signed charge
     request.
     - **`{ok, _}`** → the charge succeeded: return the original result,
       `{ok, #{ <<"body">> => Response }}`. (p4 discards the ledger's return
       value and returns the *response* body.)
     - **`{error, Error}`** → the charge failed: return `{error, Error}`
       verbatim — the ledger's error shape is propagated unchanged.
- **Returns:** `{ok, #{ body }}` when the response is delivered (free, or charged
  successfully); `{error, ...}` when pricing or charging fails.
- **Side effects:** issues a **signed** `charge` request to the ledger device,
  which is the mutation that debits the account and credits the recipient. p4's
  only commitment is the signature on that charge request (§5). No message-cache
  writes by p4 itself.

### 4.3 Non-chargable route matching (normative)

p4 decides chargability by matching the request's path against a configured
route-match list using the **`router@1.0`** `match` semantics:

- Read the list from node option `p4_non_chargable_routes` /
  `p4-non-chargable-routes`. If unset, use the **default set**:
  ```
  [ { template: "/~p4@1.0/balance" },
    { template: "/~p4@1.0/topup" },
    { template: "/~meta@1.0/*" } ]
  ```
- Build a `router@1.0` message `{ device: "router@1.0", routes: <the list> }` and
  resolve its `match` key with **that router message as the AO-Core base** (so
  `match` reads the routing table from the base's `routes`), passing a request that
  supplies the original request's `path` as the **`route-path`** (so matching is
  against the request path). Concretely:
  `resolve({ device: "router@1.0", routes: <list> }, { path: "match", route-path:
  <request path> }, Opts)`. Do **not** invert these — the routes ride on the
  **base**, the matched path rides on the request's `route-path`; the request
  singleton is the *subject being matched*, not the AO-Core base of the resolve.
- **Interpretation of the match result:**
  - If `match` reports **no matching route** (the `no_matching_route`/
    `no-matching-route` outcome), the request **IS chargable** (it did not match
    any exemption). p4 returns `true` from its chargability test.
  - **Any other** outcome means the request is **NOT chargable**; p4 returns
    `false`. This covers not only a matched route but **also any router/match fault**
    — any result other than the exact `no_matching_route` is treated as a match.
    ⚠ **Security: the gate therefore fails _open_.** A malformed
    `p4_non_chargable_routes` configuration (or any other `match` fault) yields
    free, *uncharged* requests rather than an error, so operators MUST keep that
    configuration well-formed. A conformant implementation MUST reproduce this
    fail-open behaviour (do **not** "fail closed" by treating a fault as chargable —
    that would diverge from the reference).
- The route syntax, templates, and wildcard semantics are exactly those of
  `router@1.0`. p4 adds no matching logic of its own.

### 4.4 Pricing-device contract (normative — what p4 requires of it)

The configured pricing device MUST answer the following keys. Its **base** is
the p4 handler configuration message (so it may read its own config keys from
there); the **request** is as specified. Returns are non-negative integers, the
integer `0`, or the binary `infinity`.

- **`estimate`** — *estimate the cost before evaluation.* Called in the
  pre-request hook, and as the post-response fallback when `price` errors.
  - **Request keys:** `request` (the raw singleton — the device reads the
    request's signers/path from here), `body` (the message sequence being
    priced). p4 sets `path => estimate`.
  - **MUST return** one of: `{ok, infinity}` (refuse under all circumstances),
    `{ok, 0}` (free), `{ok, N}` with `N` a positive integer (the estimated
    amount). A **non-`ok`-tagged** result (e.g. `{error, _}`) causes p4 to
    **deny** the pre-request (§4.1 step 4) or, in the post path, to surface the
    error (§4.2). (p4 distinguishes only the `ok` tag and the `infinity`/`0`
    special values; it does not itself reject a malformed `{ok, _}` price.)
- **`price`** — *finalise the cost after evaluation.* Called in the
  post-response hook.
  - **Request keys:** `request` (the raw singleton), `body` (the evaluation
    **result**). p4 sets `path => price`.
  - **MUST return** `{ok, infinity}` | `{ok, 0}` | `{ok, N}` as for `estimate`.
    A device that prices statically (the cost is fully known before execution)
    MAY omit `price` and return an error / not implement the key; p4 falls back
    to `estimate` (§4.2). A device whose final cost depends on execution (e.g. a
    metering policy) implements `price` to read the consumed resources.

The semantics of the three return values are p4's contract, identical in both
keys:
- `infinity` → p4 will not serve the request (pre: deny; the value MUST NOT be
  passed to the ledger).
- `0` → free; p4 proceeds and performs **no** ledger interaction for this
  request.
- positive integer → the amount p4 will (pre) compare against the balance and
  (post) hand to the ledger as the charge `quantity`.

### 4.5 Ledger-device contract (normative — what p4 requires of it)

The configured ledger device MUST answer the following keys. Its **base** is the
p4 handler configuration message; the **request** is as specified.

- **`balance`** — *report an account's spendable balance.* Called in the
  pre-request balance check and by p4's own `balance` key (§4.7).
  - **Request keys (as p4 sends them):** `request` (the raw singleton);
    `target` (the account whose balance is wanted — set by p4 to the request's
    sole signer, or the binary `unknown` for an unsigned request, or the list of
    signers for a multi-signer request). When invoked via p4's `balance` key,
    p4 forwards the caller's own request as `request` and does **not** set
    `target` (the ledger resolves the account from the request's signer itself).
  - **MUST return** one of: `{ok, true}` or `{ok, infinity}` (the account is
    guaranteed sufficient — p4 allows without a numeric comparison), or
    `{ok, N}` with `N` a number (p4 allows iff `N >= Price`). `{error, _}` causes
    p4 to deny the pre-request with HTTP `500`.
- **`charge`** — *debit an account and credit a recipient.* Called in the
  post-response hook, on a request **signed by the node**.
  - **Request keys (as p4 sends them):** `quantity` (the positive integer amount
    — the price); `account` (the account to debit — the request's sole signer,
    or the list of signers); `recipient` (the address to credit — see §4.2 step
    4); `request` (the raw singleton). The whole charge request is **committed
    by the node's key**, so the ledger MAY require and verify that the node
    authorised the charge.
  - **MUST return** `{ok, _}` on success (the return value is **ignored** by p4;
    any `ok`-tagged value suffices) or `{error, Error}` on failure (p4
    propagates `Error` unchanged to the client). A ledger that declines to
    charge (e.g. an allow-list policy that takes no payment) returns
    `{ok, true}`.

p4 does **not** require the ledger to implement any other key (e.g.
`credit`/`topup`); such keys are policy extensions a ledger device MAY expose
for operators/users but are **outside p4's contract**.

### 4.6 Deny results and HTTP status (normative)

Every p4 deny is an `{error, M}`. The shapes are:

| Condition | `M` |
|---|---|
| Pricing returned `infinity` (pre-request) | the binary `Node will not service this request under any circumstances.` (a bare binary, not a map) |
| Pricing returned a non-`ok`-tagged result (pre-request) | `{ type: <result-tag>, body: <<"Could not estimate price of request.">> }` |
| Insufficient funds (balance `< price`) | `{ status: 402, body: <<"Insufficient funds">>, price: <Price>, balance: <Balance> }` |
| Ledger errored on the balance check | `{ status: 500, body: <<"Error checking ledger balance.">> }` |
| Pricing could not be determined (post-response, after estimate fallback) | the pricing device's `{error, E}` value, propagated unchanged |
| Charge failed (post-response) | the ledger device's `{error, Error}` value, propagated unchanged |

A deny carrying a `status` integer MUST cause the node to respond with that HTTP
status (notably **`402 Payment Required`** for insufficient funds and **`500`**
for a ledger fault). A deny that is a bare binary or a map without `status` is
still a hard failure of the hook pipeline: the node MUST NOT serve the request,
and surfaces the error to the client (default error status). The pre-request
deny halts the pipeline **before** evaluation; a post-response deny replaces the
already-computed result with the error so the client does not receive an unpaid
result.

### 4.7 `balance` — query an account's balance through the ledger

- **Signature:** `balance(Base, Req) -> {ok, Balance} | {error, ErrMsg}`.
- **Reads:** the node's installed `request`-hook handler(s) (to discover the
  configured `ledger-device`); `Req` (forwarded to the ledger).
- **Behaviour:**
  1. Locate the node's `request`-hook handler configuration. (This is the same
     handler message that gates requests; p4's `balance` key reuses its
     `ledger-device` setting rather than requiring separate configuration.)
     - If there is **no** `request` hook installed, return
       `{error, <<"No request hook found.">>}`.
     - Otherwise take the (first) handler message as `Handler`.
  2. Read `ledger-device` from `Handler`. Build the ledger base (`Handler` with
     `device => ledger-device`) and resolve its `balance` key with
     `{ path: "balance", request: <Req> }` — i.e. forward the *incoming* request
     as the ledger's `request`, with **no** `target` (the ledger derives the
     account from the request's own signer).
  3. Return the ledger's result: `{ok, Balance}` or `{error, Error}` verbatim.
- **Returns:** `{ok, Balance}` (the ledger's balance value, an integer for the
  common case) or `{error, ...}`.
- **Side effects:** none of its own (a balance query). Reachable at the path
  `~p4@1.0/balance`, which is in the default non-chargable set so querying one's
  balance is itself free.

## 5. Data formats & encodings

- **Keys** are binary, lowercase, hyphenated on the wire: `pricing-device`,
  `ledger-device`, `body`, `request`, `path`, `target`, `quantity`, `account`,
  `recipient`, `status`, `price`, `balance`. Node options use the
  `p4_non_chargable_routes` / `p4-non-chargable-routes` family (both spellings
  accepted).
- **Addresses** (`account`, `recipient`, the signer values, `operator`,
  `p4_recipient`) are **base64url** account addresses (43 chars for 32-byte
  keys), never hex. p4 normalises configured recipient/operator addresses to
  their human-readable (base64url) form before placing them in the charge
  request. The no-signer / unknown sentinels are the literal binary `unknown`.
- **Price / quantity / balance** are numbers. The price returned by the pricing
  device is `infinity` (the literal binary), the integer `0`, or a positive
  integer; the `quantity` p4 sends to `charge` is that positive integer.
- **The charge request is a committed (signed) message** — committed with the
  **node's** key (the node's configured wallet), using the default commitment
  device. The ledger therefore sees the node as the charge's signer, distinct
  from the user who signed the original request (which travels inside the charge
  request under `request`). p4 produces no other commitments and no
  content-addressed IDs of its own.
- **`infinity` sentinel:** the binary `infinity`. p4 treats it specially in both
  the pricing result (refuse) and the ledger `balance` result (guaranteed
  sufficient). Implementations MUST compare against the binary value, not a
  numeric infinity.

## 6. Ordering, freshness & caching

- **Two-phase, per-request.** For one HTTP request the pre-request hook runs
  once before evaluation and the post-response hook runs once after. p4 keeps no
  state between them beyond what the ledger device persists; the account, price,
  and recipient are re-derived in each phase from the (same) raw singleton and
  node options.
- **Pricing is consulted twice** (estimate pre, price post) and the two values
  need not agree: the pre-request `estimate` gates on a *forecast*; the
  post-response `price` settles the *actual* cost (which a dynamic pricing device
  may compute from what the evaluation consumed). p4 charges the post-response
  figure, not the pre-request estimate.
- **No result caching by p4.** p4 performs no AO-Core message-cache or store
  writes. Because it runs as a hook, a node SHOULD configure hook resolution to
  bypass the result cache (so each request is actually gated/charged rather than
  served a cached hook result); this is node configuration, not device
  behaviour.
- **Determinism.** Given identical config, identical node options, an identical
  raw singleton, and identical sub-device behaviour, p4's allow/deny decision
  and the charge request it emits are determined entirely by the sub-device
  replies. p4 introduces no nondeterminism of its own (no clocks, no randomness).
- **Account resolution is order-insensitive** except where the signer list
  matters: a single-signer request yields a scalar account; a multi-signer
  request yields the signer **list** (its order is the order reported by the
  message's committer surface, which is unspecified — see message@1.0).

## 7. Security & authority

- **Fail-open when unconfigured; fail-closed once configured.** With `pricing-`
  or `ledger-device` unset, p4 allows every request free (§4.1 step 3). This is
  deliberate so a fresh node is usable, and is why an operator **MUST** set both
  devices to actually charge. Once both are set, a chargable request is denied
  unless pricing yields `0` *or* the ledger confirms sufficiency — i.e. the gate
  is closed by default for paid routes.
- **The caller is the request's signer.** p4 derives the account from the
  request's commitments via the standard signer/committer surface
  (`message@1.0`). A request with **no** valid signature has account `unknown`:
  in the pre-request balance check this typically yields a zero/absent balance
  and so a `402` for any positive price; ledger policies decide the exact
  outcome. Operators relying on payment MUST therefore require signed requests
  (an unsigned request cannot be attributed to a paying account).
- **The node, not the user, authorises charges.** The post-response `charge`
  request is **committed with the node's key**. This lets a ledger device verify
  that the charge was issued by the node (the entity entitled to debit accounts
  for service), not forged by a user. The user's own signature is preserved
  inside the charge request under `request`, so the ledger can still attribute
  the debit to the correct account while trusting the node's authority to apply
  it.
- **Non-chargable routes are an exemption, not an authorization bypass.**
  Matching the non-chargable set only skips pricing/charging; it does not grant
  any additional privilege. The defaults exempt balance/top-up introspection and
  the meta device so that paying for service does not require paying to *check*
  whether you can pay, or to read node metadata.
- **Recipient precedence is trust-sensitive.** Funds charged are credited to
  `p4_recipient` if a valid address, else the node `operator`, else `unknown`.
  A misconfigured node with neither set credits an `unknown` recipient; a ledger
  device SHOULD treat that as it sees fit (e.g. burn, or reject). p4 does not
  validate that the recipient is a real account.
- **Error propagation.** On a ledger or pricing fault p4 fails closed: it denies
  (pre) or converts the result into an error (post) rather than serving an
  unpaid response. It never "allows on error" for a chargable, configured
  request — the only allow-on-no-decision is the unconfigured/non-chargable case.

## 8. Errors

Every error p4 can return, and its trigger:

- `<<"Node will not service this request under any circumstances.">>` — the
  pricing device returned `{ok, infinity}` in the pre-request hook. A bare
  binary (hard deny, no HTTP status field).
- `{ type, body: <<"Could not estimate price of request.">> }` — the pricing
  device's pre-request `estimate` returned a **non-`ok`-tagged** result (e.g.
  `{error, _}`). `type` carries the result's tag (e.g. `error`). (A malformed
  `{ok, _}` is *not* caught here — it is treated as a price; §4.1 step 4.)
- `{ status: 402, body: <<"Insufficient funds">>, price, balance }` — the
  ledger's `balance` reply was a number strictly less than the estimated price.
  Drives HTTP `402`.
- `{ status: 500, body: <<"Error checking ledger balance.">> }` — the ledger
  device returned `{error, _}` to the pre-request balance check.
- `<<"No request hook found.">>` — the `balance` key was resolved on a node that
  has no `request` hook installed (so no ledger device can be discovered).
- **Propagated pricing error** — in the post-response hook, when `price` errored
  *and* the `estimate` fallback also errored, p4 returns that
  `{error, PricingError}` unchanged.
- **Propagated ledger error** — in the post-response hook, when `charge`
  returned `{error, Error}`, p4 returns it unchanged.

p4 introduces no other error atoms. Error atoms that p4 *originates* are
human-readable binaries / maps as above (not single-word atoms); errors it
*propagates* keep whatever shape the sub-device produced. Where p4 sets a numeric
`status`, the node MUST honour it as the HTTP response status.

## 9. Composition

- **Installed as `on/request` and `on/response` hooks.** The operator places a
  message bound to `p4@1.0` (carrying `pricing-device` + `ledger-device`) under
  the node's `on` configuration for **both** the `request` and `response`
  events — conventionally the *same* message for both, so the pre-gate and
  post-charge share one configuration. The node's request pipeline invokes the
  `request` handler before evaluation and the `response` handler after; an
  `{ok, NewReq}` continues the pipeline, a non-`ok` result halts it (and, for
  `response`, replaces the result with the error).
- **Pipeline position.** p4 reads the request's signer and path and passes
  `body` through unchanged on allow, so it composes with other `request`/
  `response` handlers (e.g. a rate limiter). Placing p4 in the chain means an
  upstream handler may transform the request before p4 prices it, and a
  downstream handler runs only if p4 allowed. p4 does not set a `device` key on
  its result and does not redirect resolution; its allow result is just
  `{ body }`.
- **Sub-device delegation is by device-override on the shared config.** p4 calls
  the pricing and ledger devices by resolving the *handler configuration
  message* with `device` overridden to the sub-device name. Consequently a
  policy device receives p4's whole config as its base and can read its own
  operator settings from there (e.g. a Lua ledger client reading `ledger-path`
  and `module` from the same message). A device may serve as **both** roles
  (e.g. `simple-pay@1.0` implements `estimate`, `price`/`charge`, and `balance`),
  in which case both `pricing-device` and `ledger-device` name it.
- **Policy examples (informative).**
  - `faff@1.0` — allow-list: `estimate` returns `0` for admissible signers and
    `infinity` for everyone else; `charge` returns `{ok, true}` and takes no
    payment; it has no real `balance`. Used as both pricing and ledger device,
    it gates by identity without money.
  - `simple-pay@1.0` — flat per-message pricing with an in-node ledger:
    `estimate`/`price` count messages × a configured unit price (operator
    requests free), `balance` reads the ledger, `charge` debits the signer. Acts
    as both devices.
  - `metering@1.0` — dynamic pricing: `estimate` opens a resource-metering
    session, `price` closes it and returns the integer charge from measured
    consumption. A pricing device only; paired with a separate ledger device.
- **The `balance` key as a public endpoint.** Callers query their own balance at
  `~p4@1.0/balance` (in the default non-chargable set, so free). This key
  bridges to whatever ledger the node runs without the caller needing to know
  the ledger device's name.

## 10. Conformance (normative checklist)

An implementation MUST exhibit all of the following. Items are checkable by
driving signed HTTP requests at a node configured with `p4@1.0` as its
`request`/`response` hooks over a known pricing+ledger policy (e.g.
`simple-pay@1.0` or `faff@1.0`), or by code review of the deny paths.

1. **Three keys only.** The device answers `request`, `response`, and `balance`,
   and no other key (other keys fall through to `message@1.0`).
2. **Unconfigured pass-through.** When `pricing-device` or `ledger-device` is
   unset, a chargable request is allowed and nothing is charged; the pre-request
   hook returns `{ok, #{ body }}` with the message sequence passed through.
3. **Non-chargable exemption.** A request whose path matches the non-chargable
   route set (default: `/~p4@1.0/balance`, `/~p4@1.0/topup`, `/~meta@1.0/*`, or
   the configured `p4_non_chargable_routes`) bypasses pricing and charging in
   both hooks; matching uses `router@1.0` `match` with the request path as
   `route-path`, and "no matching route" means **chargable**.
4. **Estimate gate — infinity.** A chargable request for which the pricing
   device's `estimate` returns `infinity` is **denied** pre-evaluation with the
   binary "Node will not service this request under any circumstances."; the
   request is not evaluated.
5. **Estimate gate — zero.** When `estimate` returns `0`, the request is allowed
   without any ledger `balance` call.
6. **Balance check.** When `estimate` returns a positive `Price`, p4 resolves the
   ledger's `balance` with `target` = the request's sole signer (or `unknown` if
   unsigned, or the signer list if multi-signed) and the raw request; it allows
   on `{ok, true}`, `{ok, infinity}`, or `{ok, B}` with `B >= Price`, and denies
   with HTTP `402` (body "Insufficient funds", plus `price` and `balance`) when
   `B < Price`.
7. **Balance fault.** A `{error, _}` from the ledger `balance` denies the
   pre-request with HTTP `500` and body "Error checking ledger balance.".
8. **Estimate fault.** A pre-request `estimate` that returns a non-`ok`-tagged
   result (e.g. `{error, _}`) denies with body "Could not estimate price of
   request." and a `type` field carrying the result's tag.
9. **No pre-charge.** The pre-request hook performs only a balance **read**; it
   issues no `charge`. (Verifiable: a request that is allowed but whose response
   never runs leaves the ledger unchanged from the pre-request alone.)
10. **Post price + estimate fallback.** The post-response hook resolves the
    pricing device's `price` (request body = the evaluation **result**); if
    `price` returns `{error, _}` it retries with `estimate`; a price of `0`
    charges nothing.
11. **Signed charge.** For a positive post-response price, p4 resolves the
    ledger's `charge` with `quantity` = price, `account` = the request's signer
    (list if multi-signed), `recipient` per precedence
    (`p4_recipient` → `operator` → `unknown`), and `request` = the raw singleton,
    and the **charge request is committed with the node's key** (the node, not
    the user, is the charge's signer).
12. **Charge outcome.** On `{ok, _}` from `charge`, p4 returns the original
    response body (the ledger's return value is discarded); on `{error, Error}`
    it returns that error unchanged (the client does not receive the unpaid
    result).
13. **Recipient precedence.** The charge `recipient` is `p4_recipient` if a valid
    address, else `operator`, else the binary `unknown`; configured addresses are
    emitted in human-readable base64url form.
14. **`balance` endpoint.** Resolving `~p4@1.0/balance` discovers the node's
    `request`-hook handler, reads its `ledger-device`, and returns that ledger's
    `balance` for the caller's own (signed) request; with no `request` hook
    installed it returns the error "No request hook found.".
15. **Allow body integrity.** Every allow result is exactly `{ok, #{ body }}`
    carrying the unchanged message sequence (pre) or evaluation result (post);
    p4 adds no other keys and does not set a `device` key on the result.
16. **End-to-end (with a real policy).** Under `simple-pay@1.0` as both devices:
    a signed request from a funded account succeeds and the account's balance
    decreases by the charged amount while the recipient's increases by the same
    amount; a request from an unfunded account is rejected; querying
    `~p4@1.0/balance` returns the pre-charge balance. Under `faff@1.0`: a request
    signed by an allow-listed address succeeds and one signed by a non-listed
    address is rejected, with no balances kept.

## 11. Out of scope

- The internal representation of messages, balances, and ledgers; p4 holds no
  ledger of its own.
- The pricing and ledger **policies** themselves — how a price is computed, how
  balances are stored, top-up/credit flows, multi-signer charge splitting. Those
  belong to the configured sub-devices (see their own specs). This spec pins only
  the **contract** p4 calls them through (§4.4–§4.5).
- The `router@1.0` route-match algorithm (templates, wildcards) — referenced, not
  redefined.
- The HTTP transport, how `on`-hooks are invoked by the node pipeline, and how a
  returned `status` becomes an HTTP response code — platform concerns. p4 only
  guarantees it *emits* the documented `status` values.
- Result-cache configuration for hooks (a node setting), performance, and
  concurrency of the ledger.

## Open questions

- **No-signer account in the post charge.** The pre-request balance check
  substitutes the binary `unknown` for a request with no signer, but the
  post-response charge's `account` derivation handles only the sole-signer and
  multi-signer cases — a no-signer request reaching the charge step has no
  explicit `unknown` fallback. In practice an unsigned request that priced
  positively is denied at the pre-request `402` and never reaches the
  post-response charge, so the case may be unreachable; a reimplementer should
  preserve that asymmetry (pre: `unknown`; post: no `unknown` branch) to match,
  and treat a no-signer charge as a should-not-occur state rather than inventing
  a fallback.
- **Multi-signer balance check vs. charge.** Both the pre-request `balance`
  `target` and the post `charge` `account` are set to the **list** of signers
  when a request has several. How a ledger device interprets a list-valued
  account (charge all? split? reject?) is the ledger's concern and is not pinned
  here; p4 merely forwards the list. A reimplementer must forward the list
  unchanged rather than collapsing it to one signer.
- **`infinity` from the pricing device in the post hook.** §4.4 allows `price`
  to return `infinity`, but the post-response hook's price interpretation pins
  only `0`, positive, and `{error, _}`. An `infinity` price post-evaluation is
  not given an explicit branch; since the request was already gated pre-evaluation
  (an `infinity` estimate would have denied it), this is expected to be
  unreachable. A reimplementer should not invent a charge for an `infinity`
  post-price; the safe reading is that it does not occur for a request that
  passed the pre-gate.
- **Configuration key location.** p4 reads `pricing-device`/`ledger-device` from
  the **handler configuration message** (its `Base`), not from node options. (An
  older description referred to `p4_pricing-device`/`p4_ledger-device` node
  settings; the observable behaviour pinned here — and matched by the policy
  examples — is the handler-message form.) A reimplementer MUST read these two
  keys from the message bound under `on`, overriding that message's `device` to
  call the sub-device.
- **`balance` discovery picks the first handler.** When several `request`-hook
  handlers are installed, p4's `balance` key uses the first one's
  `ledger-device`. If a node stacks multiple gating handlers with different
  ledgers, which one answers `~p4@1.0/balance` is the first; this is pinned as
  "first handler" but flagged as a likely single-handler assumption.
